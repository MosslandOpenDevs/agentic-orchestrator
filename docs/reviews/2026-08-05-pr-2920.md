## 결론

GitHub 이슈 수명주기 기능의 기본 방향은 타당하지만, 현재 구현은 진행 중인 작업을
`not_planned`로 잘못 닫거나 DB와 GitHub 상태를 영구적으로 어긋나게 만들 수 있습니다.
아래 P1 세 건은 우선 수정하고, P2 항목도 운영 적용 전에 함께 보완하는 것을 권장합니다.

## 발견 사항

### P1-1. 진행 중인 파이프라인 작업이 `not_planned`로 종료될 수 있음

위치:

- `src/agentic_orchestrator/scheduler/issue_lifecycle.py:60-71`
- `src/agentic_orchestrator/scheduler/issue_lifecycle.py:162-164`
- `src/agentic_orchestrator/scheduler/issue_lifecycle.py:199-201`
- `src/agentic_orchestrator/scheduler/issue_lifecycle.py:223-230`

`should_age_out()`은 이슈가 열려 있는지, 봇이 생성했는지, 보호 라벨이나 댓글이 있는지,
그리고 생성 후 며칠이 지났는지만 확인합니다. 실제 DB 워크플로 상태는 확인하지 않습니다.

그 결과 다음 이슈가 30일을 넘으면 `not_planned`로 닫힐 수 있습니다.

- 승격됐지만 아직 플랜 생성이 완료되지 않은 아이디어
- 프로젝트 상태가 `pending`, `generating`, `error`인 플랜
- 사람이 `promote:to-plan` 또는 `promote:to-dev` 라벨을 붙여 작업을 요청한 이슈
- `status:planned` 또는 `status:in-dev` 상태지만 아직 완료되지 않은 이슈

특히 구현 주석은 미완료 프로젝트가 플랜 이슈를 열린 상태로 유지해야 한다고 명시하지만,
이후 에이징 단계가 그 조건을 무효화합니다. 관련 단위 테스트는 이슈 생성 시각을 현재에
가깝게 설정해 이 결함을 드러내지 못합니다.

권장 수정:

- DB에서 활성 파이프라인에 연결된 이슈 번호를 에이징 후보에서 명시적으로 제외합니다.
- 에이징 대상을 실제 `status:backlog` 이슈로 제한합니다.
- 사람의 작업 지시를 나타내는 promotion 라벨도 engagement로 취급합니다.
- 오래된 `generating` 프로젝트와 플랜 없는 `promoted` 아이디어에 대한 회귀 테스트를 추가합니다.

### P1-2. `completed` 보정 실패가 같은 실행에서 `not_planned` 닫기로 바뀔 수 있음

위치:

- `src/agentic_orchestrator/scheduler/issue_lifecycle.py:175-186`
- `src/agentic_orchestrator/scheduler/issue_lifecycle.py:210-221`
- `src/agentic_orchestrator/scheduler/issue_lifecycle.py:223-230`

DB를 기준으로 완료된 이슈를 `completed`로 닫으려다 실패하면 해당 이슈는
`open_issues`에 그대로 남습니다. 이후 같은 실행의 에이징 단계가 그 이슈를 다시 검사하고,
두 번째 PATCH가 성공하면 `not_planned`로 닫습니다.

첫 번째 시도에서 lifecycle 댓글은 성공하고 PATCH만 일시적으로 실패했더라도,
에이징 단계가 보는 객체는 최초 목록의 스냅샷이므로 댓글 수는 여전히 0입니다. 따라서
완료된 작업이 잘못된 종료 사유로 닫히는 정상적인 실패 경로가 존재합니다.

권장 수정:

- DB에서 완료로 판정한 이슈는 GitHub 호출 성공 여부와 무관하게 현재 실행의 에이징
  후보에서 제거합니다.
- 실패한 `completed` 닫기는 다음 주기에 동일한 종료 사유로만 재시도합니다.
- 댓글 성공 후 PATCH 실패를 재현하는 테스트를 추가합니다.

### P1-3. 최신 500행만 반복 조회해 오래된 완료 항목이 영구적으로 보정되지 않음

위치:

- `src/agentic_orchestrator/scheduler/issue_lifecycle.py:156`
- `src/agentic_orchestrator/scheduler/issue_lifecycle.py:193`
- `src/agentic_orchestrator/db/repositories.py:250-258`
- `src/agentic_orchestrator/db/repositories.py:537-545`

승격 아이디어와 플랜을 각각 최신순 500개로 제한해 조회합니다. GitHub 이슈를 닫아도
DB 행은 삭제하거나 상태를 변경하지 않으므로, 다음 실행에서도 동일한 최신 500개를
다시 읽습니다. 501번째 이후의 오래된 항목에는 영원히 도달하지 않습니다.

그 결과 이미 플랜이나 프로젝트가 존재하는 오래된 이슈가 `completed`로 보정되지 않고
`not_planned`로 에이징되거나, 보호 라벨 또는 댓글이 있다면 계속 열린 상태로 남습니다.

권장 수정:

- offset 기반으로 저장소 결과를 끝까지 페이지 처리합니다.
- 더 효율적으로는 GitHub에서 가져온 열린 이슈 번호를 기준으로 DB 레코드를 직접 조회합니다.
- 500개를 초과하는 레코드를 사용해 501번째 항목까지 보정되는 회귀 테스트를 추가합니다.

### P2-1. `issue_lifecycle.enabled: false`가 인라인 닫기를 비활성화하지 않음

위치:

- `src/agentic_orchestrator/scheduler/tasks.py:959-967`
- `src/agentic_orchestrator/scheduler/tasks.py:1546-1547`
- `docs/labels.md:134-135`

설정의 `enabled` 값은 예약된 backlog sweep만 제어합니다. 새 아이디어를 플랜으로 승격할
때 실행되는 인라인 닫기는 이 설정을 확인하지 않습니다.

문서는 이 설정으로 전체 lifecycle 메커니즘을 끌 수 있다고 설명하지만, 실제로는
`false`로 설정해도 새 아이디어 이슈에 댓글을 달고 라벨을 변경한 뒤 닫습니다.

권장 수정:

- 이미 로드한 `backlog_config["issue_lifecycle"]["enabled"]` 값을 인라인 경로에도 적용합니다.
- 비활성화 상태에서 댓글, 라벨 변경, 닫기 호출이 모두 발생하지 않는 테스트를 추가합니다.

### P2-2. DB 커밋 전에 GitHub 이슈를 닫아 복구 불가능한 상태 불일치가 생김

위치:

- `src/agentic_orchestrator/scheduler/tasks.py:959-980`
- `src/agentic_orchestrator/scheduler/tasks.py:994`
- `src/agentic_orchestrator/db/repositories.py:481-486`

`PlanRepository.create()`는 `flush()`만 수행하고 트랜잭션을 커밋하지 않습니다. 하지만
아이디어 GitHub 이슈는 즉시 `completed`로 닫힙니다. 실제 DB 커밋은 모든 아이디어 처리와
승인 플랜의 프로젝트 생성까지 끝난 뒤에 실행됩니다.

이 사이에 PM2 취소, 프로세스 종료, 프로젝트 생성 중 예외 또는 최종 커밋 실패가 발생하면
DB 플랜은 롤백되지만 GitHub 이슈는 `planned/closed`로 남습니다. 보정 스윕은 열린 이슈만
조회하므로 이 불일치를 재개방하거나 복구하지 못합니다.

권장 수정:

- DB 커밋이 성공한 뒤 GitHub 닫기를 실행합니다.
- 더 안전하게는 outbox 또는 post-commit reconciliation 패턴을 사용합니다.
- 커밋 실패와 취소를 주입해 GitHub가 닫히지 않는 테스트를 추가합니다.

### P2-3. 전체 댓글 수를 사람의 관심으로 간주해 봇 댓글 이슈가 영구 보호됨

위치:

- `src/agentic_orchestrator/github_client.py:109`
- `src/agentic_orchestrator/github_client.py:125`
- `src/agentic_orchestrator/scheduler/issue_lifecycle.py:66-67`
- `src/agentic_orchestrator/backlog.py:950-960`
- `src/agentic_orchestrator/backlog.py:1170-1193`

GitHub 이슈 객체에는 작성자 정보 없이 전체 댓글 수만 저장됩니다. lifecycle은 댓글이
하나라도 있으면 사람의 관심으로 판단하지만, 기존 `BacklogOrchestrator`도 열린 플랜
이슈에 자동 댓글을 작성합니다.

따라서 사람이 전혀 관여하지 않은 봇 생성 플랜이 에이징에서 영구 제외됩니다. 반대로
사람이 댓글 없이 라벨, 할당, reaction 또는 reopen으로 관심을 표시한 경우는 감지하지
못합니다.

또한 lifecycle은 댓글을 먼저 쓰고 라벨/PATCH를 나중에 수행합니다. PATCH가 실패하면
다음 재시도마다 같은 댓글이 추가되며, 정의된 `LIFECYCLE_SIGNATURE`는 중복 방지에
사용되지 않습니다.

권장 수정:

- 에이징 직전 댓글 작성자 정보를 조회해 비봇 댓글만 engagement로 인정합니다.
- promotion 라벨과 명시적인 curation 상태도 별도로 보호합니다.
- 기존 lifecycle signature가 있으면 같은 댓글을 다시 쓰지 않도록 멱등성을 보장합니다.

### P2-4. 모든 이슈를 조회한다고 설명하지만 1,000개 API 항목에서 중단됨

위치:

- `src/agentic_orchestrator/github_client.py:382-383`
- `src/agentic_orchestrator/github_client.py:407-424`
- `src/agentic_orchestrator/scheduler/issue_lifecycle.py:147-150`

`list_issues()`는 lifecycle처럼 모든 이슈를 봐야 하는 경로를 위한 메서드라고 설명하지만,
기본값은 페이지당 100개, 최대 10페이지입니다. Pull Request도 API 페이지 크기에 포함된
뒤 로컬에서 제거되므로 실제 이슈 수는 1,000개보다 적을 수 있습니다.

문서에 기록된 2,866개 이슈 상황에서는 오래된 항목이 조회되지 않습니다. 최신 1,000개가
보호 라벨, 봇 댓글 또는 젊은 생성 시각 때문에 닫히지 않으면 오래된 이슈는 계속 보이지
않아 영구적으로 처리되지 않습니다.

권장 수정:

- API 응답이 끝날 때까지 페이지를 순회합니다.
- 안전 상한이 반드시 필요하다면 불완전 조회를 명시적으로 기록하고 다음 실행에서 cursor나
  page offset을 이어갑니다.
- 10페이지를 넘는 pagination 테스트와 PR이 섞인 페이지 테스트를 추가합니다.

### P2-5. rate limit 이후에도 실패 요청을 계속 반복함

위치:

- `src/agentic_orchestrator/scheduler/issue_lifecycle.py:119-121`
- `src/agentic_orchestrator/scheduler/issue_lifecycle.py:157-158`
- `src/agentic_orchestrator/scheduler/issue_lifecycle.py:183-186`
- `src/agentic_orchestrator/scheduler/issue_lifecycle.py:225-235`

`_close_issue()`는 `GitHubRateLimitError`를 포함한 모든 예외를 일반 실패로 삼키고
`False`를 반환합니다. 닫기 예산은 성공했을 때만 감소하므로 GitHub가 rate limit 응답을
시작한 뒤에도 조회된 전체 후보에 PATCH를 계속 시도할 수 있습니다.

따라서 `max_closes_per_run: 50`은 성공 횟수만 제한할 뿐 API mutation 시도 횟수의
보호 장치가 되지 못합니다.

권장 수정:

- `GitHubRateLimitError`는 즉시 상위로 전달해 현재 sweep을 중단합니다.
- 일반 실패도 시도 예산에 포함하거나 별도의 `max_attempts_per_run`을 둡니다.
- 첫 PATCH에서 rate limit이 발생했을 때 추가 mutation이 없는 테스트를 추가합니다.

## 권장 수정 순서

1. 활성 파이프라인 항목을 에이징에서 제외합니다.
2. 완료 보정 실패가 에이징으로 넘어가지 않게 합니다.
3. DB 500행 제한과 GitHub 1,000항목 제한을 제거하거나 cursor 기반으로 순회합니다.
4. 외부 GitHub 변경을 DB 커밋 이후로 옮깁니다.
5. lifecycle 비활성화 설정을 모든 경로에 적용합니다.
6. 댓글 작성자 기반 engagement와 멱등성 처리를 추가합니다.
7. rate limit 발생 시 sweep을 즉시 중단합니다.
